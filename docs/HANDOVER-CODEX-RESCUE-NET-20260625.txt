WHAT RESCUE-NET IS
Rescue-Net is an open disaster coordination and relief management system. It connects official command, community reports, posko, volunteers, organizations, donors, medical posts, shelters, logistics providers, transport providers, and evidence verification into one coordinated workflow.

The critical principle: raw reports are not operational truth. Raw inputs must pass location validation, duplicate/overlap checks, trust signals, operator review, and consolidation before being used as official operational data.

MAIN USER FLOWS
1. Public landing
   - Welcome page with disaster imagery and live summary cards.
   - Header menu on desktop and mobile:
     Home, War Room, About Us, Fitur/Mockup, Laporan Masyarakat, Download, Login/Registrasi.
   - Mobile header/menu was previously corrected; preserve current visual state unless owner requests layout redesign.

2. Laporan Masyarakat
   - Public users submit incident/need/evidence reports.
   - Reports must remain raw/pending until validated.
   - Location should support:
     GPS/share location,
     map point,
     official admin-area tree Provinsi -> Kabupaten/Kota -> Kecamatan -> Desa/Kelurahan,
     manual emergency location with review status.

3. Offline mobile/PWA registration
   - Installed app should let a user register offline, identify posko/organization/community role, fill posko location, fill needs, attach photos.
   - Data is stored locally first and syncs automatically when online.
   - When online, user should be prompted to link to an active disaster event or create a new event if appropriate.
   - User can choose an active organization/parent organization during online sync.
   - Offline local cache is acceptable for draft queue, but not as final official data.

4. War Room
   - Operational command view.
   - Shows consolidated needs, events, posko, logistics, evidence, and verification queues.
   - Needs scenario selector:
     minimum: ignore broad aggregate claims and use the smallest reliable overlapping posko/detail value.
     optimal: use the most reasonable value with anti-duplication logic, preferred for normal operations.
     maximum: include aggregate/broad claims plus detailed posko values, marked clearly as high-side planning.
   - Command can apply manual corrections. Corrections must remain traceable, for example total 1000 where 250 is manual correction.

5. Data Consolidation
   - The most important RN module.
   - Goal: separate raw reports/claims from official operational data.
   - New or existing data must not be blindly summed.
   - Overlapping posko in similar location/need category should use MAX by default, not SUM.
   - SUM only when operator confirms the beneficiary groups/areas are different.
   - Broad organization/province-level reports must not override village/posko detail. They should be treated as aggregate reports and shown as a separate range/assumption layer unless verified into detail.

6. Trusted Verifier / Verifikator Tepercaya
   - Allows reporters, personal posko, small organizations, communities, kitchens, transport/resource providers, or volunteers to ask a verifier who knows them.
   - Verifier can be RT/RW/Lurah/Camat/BPBD, organization leader, community coordinator, public figure, trusted local person, or RN admin.
   - Important separation:
     identity_verified is not the same as report_verified.
     location_verified is not the same as organization_verified.
     organization_verified is not the same as need/consolidated_verified.
   - Badge text must never imply all reports are true.

DATA MODEL PRINCIPLES
Location status:
- location_verified_gps: GPS accepted.
- location_verified_map_point: user selected a map point.
- location_verified_admin_area: selected official admin area down to desa/kelurahan.
- location_review: manual or unclear location.
- aggregate_report: only province/kabupaten/large-area claim.
- invalid_location: unusable.

Unit normalization:
- RN must avoid rigid database assumptions like "1 box" or "1 plastic bag" always meaning the same quantity.
- Store original_unit_label and original_quantity.
- Store normalized_unit and normalized_quantity only when conversion is known.
- If conversion unknown, keep as needs_review_unit_conversion.
- Examples:
  1 dus air mineral can vary by brand/size.
  1 kantong plastik may vary widely.
  1 karung may vary by commodity.
- Do not convert uncertain package units into final operational quantity without evidence or operator confirmation.

Conflict and anti-misinformation handling:
- Duplicate/overlap candidates should be detected by location, need type, time, reporter, posko name, beneficiary group, evidence, and distance.
- Recommended default for same place/same need/same beneficiary group is MAX, not SUM.
- Broad organization reports should be displayed as aggregate/range layer and traceable to source.
- Detailed posko/village reports should remain drill-down traceable.
- Operator can merge, separate, reject, request more evidence, escalate to posko, or convert to logistic need.

LOCATION TREE SOURCE PLAN
Use official Indonesia administrative master data:
- Master dropdown: Kemendagri/data.go.id KODE ADMINISTRASI WILAYAH or DATA MASTER KODE DESA/KELURAHAN.
- BPS bridging: BPS SIG Bridging Kode when matching BPS statistics with Kemendagri codes.
- Village/kelurahan boundary maps: BIG administrative boundaries for reverse-checking GPS/map point.
- Demographic support: BPS/Dukcapil/Open Data daerah as supporting data, not as primary dropdown source.
