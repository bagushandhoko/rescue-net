Rebuild API:

  cd /volume1/docker/rescue-net-api
  sudo /usr/local/bin/docker build -t rescue-net-api:0.1 .
  sudo /usr/local/bin/docker rm -f rescue-net-api
  sudo /usr/local/bin/docker run -d \
    --name rescue-net-api \
    --restart unless-stopped \
    --env-file /volume1/docker/rescue-net-api/.env \

back to localhost.

============================================================
5. CONSOLIDATION BEHAVIOR
============================================================

Raw reports are not operational facts.

Location status distinguishes GPS, map point, official admin area, manual
location, aggregate report, and invalid location.

Duplicate detection covers:
  need
  community_report
  posko

Safe first pass:
  use MAX, not SUM, when reports may overlap.

National rollup:
  minimum = smallest value for same relative area, aggregate excluded
  optimal = consolidated detail, MAX per posko/detail
  maximum = optimal plus aggregate context

Trace path:
  national item -> province/city/district/village -> posko -> raw source IDs

Aggregate province/city/district values are command context unless explicitly
included by maximum scenario.

Manual command correction:
  never overwrite raw data
  store original value
  store corrected value
  store delta
  store actor, reason, note, timestamp
  display manual contribution in War Room

Unknown units such as one sack, one box, or one plastic bag must remain in
unit review unless a trusted conversion exists.

============================================================
6. TRUSTED VERIFIER
============================================================

Trusted Verifier is operational.

Never use one generic "verified" badge. Keep these separate:
  identity
  location
  organization membership
  report source
  report content
  consolidated need

Tables:
  verifier_profiles
  trusted_verification_requests
  verification_endorsements

IMPORTANT DATABASE COMPATIBILITY:
An older unrelated table named verification_requests already exists. Do not
rename trusted_verification_requests back to verification_requests.

Verifier levels:
  community verifier
  organization verifier
  government verifier
  trusted public verifier
  official/RN admin verifier

Token:
  seven-day token
  only SHA-256 token hash stored
  verification URL returned by API

Responses:
  approved
  needs_correction
  not_known
  rejected

Endorsements:
  one explicit scope
  visible on profile
  revocable
  audit metadata retained

Registration:
  app supports registered verifier, invited verifier, or no verifier
  verifier data is stored locally while offline
  request is created after device registration sync succeeds

Current limitation:
  SMS/email gateway not connected; share the verification URL manually.

Schema ownership:
  API user cannot ALTER every legacy table.
  volunteer_profiles is owned by another role.
  Do not force ALTER on it. Use verification_endorsements for volunteer trust.

9. SECURITY
============================================================

Never commit:
  .env
  passwords
  GitHub token
  AI keys
  database dumps
  uploaded evidence
  real patient/victim data
  private keys

Identity endorsement is a trust signal, not proof that a report is correct.
AI must describe this distinction in its recommendations.
